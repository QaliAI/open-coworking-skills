# Sample engagement — Coworking Revenue & Operations Health Check

A complete, **100 % synthetic** engagement so anyone can see exactly what a
paid health check produces: what the client sends, the single command that
runs it, the draft a reviewer works through, and the released report.

Nothing in here is real. The data is the fictional two-location
[Northstar Coworking Demo](../synthetic-space/README.md) (`.example` addresses,
555-01xx phone numbers, enforced by an integration test).

```text
client-export/                     what the operator sends (15 canonical CSVs)
reports/northstar-demo/
  report.html                      DRAFT REPORT — REVIEW REQUIRED
  report.final.html                released version (reviewer recorded)
  REVIEW_CHECKLIST.md              the human review gate
  engagement.json                  manifest: inputs, fingerprints, metrics, status
```

## Run it yourself

```bash
python -m opencoworking.cli health-check \
  --input examples/health-check-engagement/client-export \
  --output examples/health-check-engagement/reports/northstar-demo \
  --client "Northstar Coworking Demo" \
  --as-of 2026-07-01 \
  --generated-at "2026-07-21T00:00:00+00:00" \
  --force
```

The `--generated-at` pin is only there so the committed `report.html` is
byte-reproducible; a real engagement uses the actual run time.

Then the release step (already applied to the committed `report.final.html`):

```bash
python -m opencoworking.cli health-check-finalize \
  --engagement examples/health-check-engagement/reports/northstar-demo \
  --reviewer "Sample Reviewer (open-source demo)" \
  --attest "I completed the human review checklist on the synthetic Northstar demo." \
  --notes "Synthetic dataset; checklist walked through to demonstrate release." \
  --at "2026-07-22T09:00:00+00:00" \
  --force
```

`--attest` is required. The released HTML prints the reviewer and that
statement. A green banner without both is refused. The sample attestation
records that the checklist was walked on synthetic data. It does not claim a
customer reviewed it.

`bundle.json`, `preflight.json`, and `finalized.json` are regenerated by those
commands. `bundle.json` and `preflight.json` are deliberately not committed.
`finalized.json` records the reviewer and attestation for the sample.

## What the sample proves

- Every headline number is verified against hand-computed values in
  [`tests/fixtures/synthetic_expected.json`](../../tests/fixtures/synthetic_expected.json)
  and [`tests/integration/test_health_check_engagement.py`](../../tests/integration/test_health_check_engagement.py):
  occupancy 5/7 offices, 38/66 workstations, 11,785/18,500 financially;
  $2,088/month of unbilled recurring rate; 2,350 of failed/overdue balances;
  1,400/month of list value idle on the out-of-service office; a 3,400/month
  suite departing inside 90 days.
- The committed `report.html`, `report.final.html`, and `REVIEW_CHECKLIST.md`
  are byte-identical to a fresh run from this directory, so the sample can never
  quietly drift from the engine.
- The report contains no member names, emails, or phone numbers — checked by
  test, not by eye.
